## Context

当前仓库以 OpenSpec 驱动为主，还没有 Go 代码实现。第一版目标是一个最小可运行的 CLI ChatBot，而不是过早引入 Planner、Memory、Tool Router 或多 Agent 编排。当前实现已经形成闭环，但相较初版方案又补充了三个重要约束：只使用本地配置文件、在启动阶段就拦截占位 API Key、默认把调试日志写到文件而不是终端。

## Goals / Non-Goals

**Goals:**
- 建立 `CLI -> ChatBot -> Session -> LLMClient` 的最小运行链路。
- 用稳定的数据结构表示对话消息和会话上下文。
- 用本地配置文件驱动模型连接信息，避免运行时来源过多。
- 在启动阶段尽早发现配置问题，而不是等首轮对话才暴露。
- 提供基于 `spf13/cobra` 的 CLI 入口和命令组织，支持启动聊天、退出、清空上下文和查看历史。
- 将调试与接口细节日志写入本地文件，避免打断命令行交互体验。

**Non-Goals:**
- 不实现 Tool Calling、RAG、工作流编排、长期记忆或多 Agent 协同。
- 不实现 Web UI、插件系统或复杂命令框架。
- 不在第一版解决 token 裁剪、消息摘要压缩或多 provider 并发切换。
- 不引入环境变量覆盖、远程配置中心或动态热更新。

## Decisions

### 1. 使用清晰分层目录而非单文件原型

按 `cmd/chat`、`internal/app`、`internal/session`、`internal/llm`、`internal/config` 拆分职责。

原因：
- 与仓库的演进式目标一致，后续新增能力时可以沿现有边界扩展。
- 比把逻辑全部写进 `main.go` 更容易测试和替换实现。

备选方案：
- 单文件原型开发更快，但会把 CLI、会话和模型调用耦合在一起，后续重构成本更高，因此放弃。

### 2. 用 `Message` 和 `Session` 作为第一版上下文抽象

`Message` 只保留 `Role` 和 `Content`，`Session` 在内存中顺序维护消息列表，并负责追加 user 和 assistant 消息。

原因：
- 这是后续扩展 Tool 消息、摘要消息或持久化消息的最小公共模型。
- 第一版只需要短期上下文，不必引入数据库或文件存储。

备选方案：
- 直接在 `ChatBot` 内维护字符串切片实现更少代码，但会丢失角色语义，不利于后续接入工具调用和标准聊天 API。

### 3. 用 `LLMClient` 接口隔离 provider

定义统一 `Chat(ctx, messages)` 接口，第一版仅实现 OpenAI 兼容客户端。

原因：
- 保证 `ChatBot` 主流程不依赖具体厂商。
- 兼容 OpenAI 风格接口后，可较低成本适配 DeepSeek、Qwen、兼容层代理或本地模型网关。

备选方案：
- 直接在 `ChatBot` 中发 HTTP 请求实现更快，但 provider 细节会渗透到业务层，后续扩展成本高，因此不采用。

### 4. 使用本地配置文件管理运行参数

运行时只读取 `configs/config.yaml`，并通过 `configs/config.example.yaml` 提供示例模板。

原因：
- 第一版优先保证行为简单可预测，避免同时维护文件配置和环境变量覆盖规则。
- 用示例文件加本地文件的方式，可以兼顾示例可读性和私有配置隔离。
- 排查问题时，只需要核对单一配置来源，成本更低。

备选方案：
- 环境变量覆盖机制更灵活，但会增加排查成本，也容易让实际运行值与文件内容不一致，因此当前不采用。

### 5. 在启动阶段拦截占位 API Key

对 `llm.api_key` 做启动期校验，空值和形如 `{...}` 的占位值都视为未配置。

原因：
- 用户最常见的错误是直接保留示例配置中的占位值。
- 让程序在启动时失败，比进入交互后首轮请求再报鉴权错误更容易理解和排查。

备选方案：
- 完全依赖远端接口返回 401 可以少写一点本地校验，但交互体验差，因此不采用。

### 6. CLI 基于 Cobra 组织命令入口

使用 `spf13/cobra` 管理根命令和聊天启动入口，在交互式聊天循环内部继续识别 `exit`、`quit`、`clear`、`history` 等保留输入。

原因：
- 仓库后续很可能继续增加调试、配置检查或 provider 管理命令，Cobra 更适合作为统一入口。
- 仍可保持聊天主循环简单，只把命令树和参数解析交给成熟库处理。

备选方案：
- 纯手写 CLI 循环代码更少，但一旦增加子命令或参数，入口会快速膨胀，因此不采用。

### 7. 默认把日志写入本地文件

标准库 `log` 在启动时统一重定向到 `logs/chat.log`，请求日志和调试日志不直接写标准输出。

原因：
- 命令行交互界面应该只展示 `You:`、`Bot:` 和必要错误，不应被调试日志打断。
- 保留文件日志后，仍然可以追踪请求 URL、状态码、耗时、回复摘要和错误详情。

备选方案：
- 直接输出到终端更直观，但会破坏对话体验，因此改为文件日志。

## Risks / Trade-offs

- [Risk] OpenAI 兼容实现只覆盖单轮文本回复最小路径，后续接入工具调用或流式输出时需要扩展请求与响应结构。 -> Mitigation：将消息类型和客户端接口独立定义，后续仅扩展 `llm` 包和 `ChatBot` 编排。
- [Risk] 内存会话不会控制上下文长度，长对话可能导致请求体膨胀。 -> Mitigation：配置中预留 `max_history_messages`，后续版本实现裁剪策略。
- [Risk] 基础命令和普通自然语言输入可能发生冲突，例如用户想讨论单词 `history`。 -> Mitigation：第一版接受该权衡，后续若需要可改为 `/history` 形式命令前缀。
- [Risk] 文件日志会持续增长，占用本地磁盘空间。 -> Mitigation：第一版先接受单文件追加策略，后续若日志规模增大再补 rotation。
- [Risk] 仅支持 OpenAI 兼容协议会限制某些 provider 的特性使用。 -> Mitigation：接口抽象先保留兼容层，第二阶段再按 provider 差异扩展。

## Migration Plan

这是仓库中的首次 Go 实现，不涉及线上迁移。落地步骤为：初始化模块和目录结构，添加示例配置文件和本地配置约定，实现本地 CLI 运行闭环，再补充基础测试、中文注释和使用说明。若实现不稳定，可直接回退到仅保留 OpenSpec 变更文件，不影响现有规范目录。

## Open Questions

- 是否在下一版加入流式输出支持，目前建议不做，保持同步文本回复。
- `history` 命令输出是否需要脱敏或截断，目前建议原样输出用于学习和调试。
- 日志文件后续是否需要分级与滚动切分，当前版本先保持单文件追加。
