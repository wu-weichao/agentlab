# AI Agent 后续版本演进规划

本文档基于当前仓库已经完成的 `v0.0.8 agent-runtime-lite` 规划后续演进路线。版本设计继续遵循“先简单、后复杂”的原则，每个版本只解决一个主要问题，避免同时引入多个尚未验证的抽象。

## 当前基线

当前版本已经具备：

- 配置驱动的 Prompt Runtime。
- 受预算控制的短期上下文裁剪与滚动摘要。
- `calculator`、`time`、`file_read` 和 `web_search` 工具。
- 基于 JSON 文本协议的 Tool Calling。
- 受 `MaxSteps` 限制的顺序多步工具循环。
- 单次请求内基于 `ToolCallKey` 的工具结果去重。
- 工具循环结构化日志和敏感内容脱敏。
- 独立的 `internal/agent.Agent` 与 `Agent.Run()` 入口。
- 保留兼容性的 `app.ChatBot` 适配层。

当前主要限制：

- 工具调用依赖模型生成 JSON 文本，没有接入 provider 原生 Tool Calling。
- Runtime 诊断主要依赖日志，没有稳定的结构化运行结果。
- 没有高风险工具授权机制，不能安全引入文件写入或命令执行。
- 会话只保存在内存中，没有跨进程恢复能力。
- 没有长期记忆、计划执行、Workflow、RAG 或 Multi-Agent。

## v0.0.9 native-tool-calling

### 目标

将当前依赖 Prompt 约束的 JSON 文本工具协议升级为 provider 原生 Tool Calling，减少格式错误、重复工具请求和不同模型兼容问题。

### 能力

- 扩展 `llm.Message`，表示 assistant tool call 和 tool result。
- 扩展 `llm.ChatResponse`，返回结构化工具调用。
- OpenAI 兼容客户端发送原生工具定义。
- 将 provider 工具调用转换为仓库内部统一的 `tools.ToolCall`。
- 保留现有文本 JSON 协议作为兼容模式。
- 保持顺序多步循环、`MaxSteps` 和 runCache 语义不变。

### 实现思路

```text
Provider 原生 tool_calls
        ↓
LLM Provider Adapter
        ↓
仓库统一 ToolCall
        ↓
Agent Tool Loop
        ↓
ToolExecutor
```

Provider 私有字段只允许出现在 `internal/llm` 适配层，Agent 和工具层继续依赖仓库统一协议，避免 Runtime 与 OpenAI API 强绑定。

### 可观测性

- 记录当前工具调用模式：`native` 或 `text_compat`。
- 记录 provider 返回的工具调用数量和解析状态。
- 保留 `request_id`、step、工具名、调用 key 和缓存命中字段。
- 不记录完整工具参数和敏感请求头。

### 边界

- 不支持并行工具调用。
- 一次模型响应仍只允许一个工具调用。
- 不新增工具。
- 不增加跨轮工具缓存。
- 不实现 Planner、Workflow 或 Memory。

### 下一步

在工具协议稳定后，将一次 Agent 运行过程从日志提升为结构化数据。

## v0.0.10 structured-run-trace

### 目标

让调用方能够直接获得一次 Agent 运行的步骤、工具执行和错误信息，而不需要解析日志。

### 能力

- 新增 `RunResult`，包含最终回答和运行轨迹。
- 新增 `RunStep`，区分模型调用、工具调用、缓存复用和最终回答。
- 记录步骤序号、工具名、成功状态、耗时和错误分类。
- 保留现有 `Agent.Run()` 简单接口，并增加结构化运行入口。

### 实现思路

- 运行轨迹只描述本轮执行，不直接写入会话历史。
- `Agent.Run()` 可委托新的结构化入口并只返回最终文本。
- 工具结果正文与诊断 metadata 分离。
- 错误使用稳定分类，不让调用方依赖错误字符串。

### 可观测性

- 每次运行返回总步骤数、总耗时和终止原因。
- 每个工具步骤返回 cache hit、执行耗时和错误代码。
- 日志与结构化轨迹使用同一组 request ID 和 step ID。

### 边界

- 不引入 OpenTelemetry 或指标平台。
- 不持久化运行轨迹。
- 不暴露模型隐藏推理内容。
- 不改变工具执行权限。

### 下一步

基于结构化步骤和错误分类建立统一的工具安全决策点。

## v0.0.11 tool-safety-policy

### 目标

在新增写入或命令类工具之前，建立可测试、可配置的工具风险控制机制。

### 能力

- 定义工具风险等级，例如只读、写入和命令执行。
- 为工具补充副作用和授权要求元信息。
- 新增工具调用策略接口，支持允许、拒绝和请求授权。
- 对拒绝和未授权调用返回结构化结果。
- 支持 CLI 场景中的最小确认回调。

### 实现思路

工具循环在真实执行前统一经过策略检查：

```text
ToolCall
   ↓
Safety Policy
   ├── Allow   → Execute
   ├── Deny    → Structured Error
   └── Confirm → Approval Callback → Execute / Deny
```

策略层只决定是否允许执行，不承担具体工具逻辑。

### 可观测性

- 记录工具风险等级和策略决策。
- 记录授权来源和拒绝原因。
- 不在日志中记录确认输入中的敏感信息。

### 边界

- 暂不实现复杂角色权限系统。
- 暂不实现远程审批服务。
- 不新增 shell 工具。
- 不允许模型自行绕过授权。

### 下一步

使用安全策略支撑第一个具有副作用的受控工具。

## v0.0.12 controlled-file-write

### 目标

增加工作区内受控文件写入能力，验证高风险工具的授权、边界和审计链路。

### 能力

- 新增 `file_write` 工具。
- 只允许写入配置的工作区范围。
- 默认拒绝覆盖已有文件。
- 覆盖操作必须显式声明并经过授权。
- 拒绝写入 `.git`、`.codex`、`.claude`、密钥文件和工作区外路径。
- 返回规范化路径、写入字节数和覆盖状态。

### 实现思路

- 路径校验、授权检查和实际写入分层处理。
- 写入前后都验证目标路径仍位于工作区内。
- 首版只支持完整文件写入，不实现补丁和复杂编辑协议。
- 工具失败返回结构化错误，不直接终止进程。

### 可观测性

- 记录目标相对路径、写入字节数和覆盖状态。
- 记录授权结果和安全拒绝原因。
- 不记录完整写入正文。

### 边界

- 不支持删除、移动或递归目录操作。
- 不支持任意系统路径。
- 不支持 shell 命令。
- 不保证跨多个文件的事务性。

### 下一步

在 Runtime 能安全执行读写操作后，补充跨进程会话状态。

## v0.1.0 persistent-session

### 目标

将当前内存会话升级为可保存、可恢复的本地会话，同时保持上下文裁剪和摘要语义不变。

### 能力

- 定义可版本化的会话序列化格式。
- 保存 system prompt 标识、滚动摘要和近期消息。
- 支持创建、列出、加载和删除本地会话。
- CLI 支持恢复指定会话。
- 对损坏或不兼容数据返回明确错误。

### 实现思路

- 首版采用本地 JSON 文件存储。
- 存储接口与文件实现分离，但不提前引入数据库。
- system prompt 建议保存版本或配置指纹，避免恢复后能力说明重复追加。
- 使用临时文件加原子替换降低写入中断风险。

### 可观测性

- 记录会话 ID、加载结果、保存耗时和消息数量。
- 不输出完整会话正文。
- 记录序列化版本和迁移失败原因。

### 边界

- 只支持本地单用户。
- 暂不声明多进程并发安全。
- 不对存储内容自动加密。
- 持久化会话不等于长期记忆。

### 下一步

在会话持久化之外，引入由用户或 Agent 显式维护的长期事实。

## v0.1.1 minimal-long-term-memory

### 目标

提供最小、可解释、可删除的长期记忆能力，不直接引入向量数据库。

### 能力

- 新增结构化记忆条目：内容、标签、来源和更新时间。
- 提供显式 `memory_write`、`memory_read` 和 `memory_delete`。
- 使用关键词或标签进行简单检索。
- 限制记忆数量、单条长度和注入上下文的总预算。
- 用户可以查看和清理所有记忆。

### 实现思路

- 记忆存储与 Session 存储分离。
- 只有显式工具调用才能写入长期记忆。
- 检索结果作为受控上下文注入，不自动修改 system prompt。
- 先验证记忆生命周期和隐私边界，再考虑 Embedding。

### 可观测性

- 记录记忆操作类型、条目 ID、命中数和注入字符数。
- 不在普通日志中输出完整记忆内容。
- 标记记忆来源是用户明确要求还是 Agent 建议后确认。

### 边界

- 不做向量检索。
- 不自动保存所有对话。
- 不跨用户共享记忆。
- 不把模型推测写成事实记忆。

### 下一步

在稳定的 Runtime、工具和状态基础上引入显式任务计划。

## v0.1.2 plan-execute-loop

### 目标

实现单 Agent 的最小计划执行循环，使复杂任务可以拆分、执行、观察并在失败时调整。

### 能力

- 定义结构化 Plan 和 PlanStep。
- 支持待执行、执行中、完成、失败和跳过状态。
- Agent 每次只执行一个计划步骤。
- 工具结果能够更新步骤状态。
- 步骤失败时允许有限次数重规划。

### 实现思路

```text
User Goal
   ↓
Plan
   ↓
Execute One Step
   ↓
Observe Result
   ├── Continue
   ├── Replan
   └── Finish
```

Planner 只生成和调整计划，Executor 继续复用现有工具循环，避免建立第二套工具执行机制。

### 可观测性

- 记录 plan ID、step ID、状态变化和重规划原因。
- 将计划轨迹放入结构化 RunResult。
- 区分模型失败、工具失败和策略拒绝。

### 边界

- 保持单 Agent。
- 不支持步骤并行。
- 不实现通用 DAG。
- 不允许无限重规划。

### 下一步

将已经验证的计划步骤抽象为可声明、可恢复的 Workflow。

## v0.2.0 workflow-runtime

### 目标

支持显式定义和执行稳定工作流，用于重复执行确定性较高的多步骤任务。

### 能力

- 定义工作流、步骤、输入和输出。
- 支持顺序步骤和简单条件分支。
- 支持步骤级重试、超时和失败停止。
- 支持保存执行状态并从中断点恢复。
- 工具步骤和模型步骤使用统一执行结果。

### 实现思路

- 首版采用简单有向流程，不实现任意动态图。
- Workflow 负责确定性编排，Agent Planner 负责不确定任务决策。
- 复用工具安全策略、运行轨迹和持久化接口。

### 可观测性

- 记录 workflow ID、run ID、step ID、输入摘要、输出摘要和状态迁移。
- 提供工作流执行结果和失败步骤。
- 不记录完整敏感输入输出。

### 边界

- 不支持并行步骤。
- 不提供可视化编辑器。
- 不实现分布式调度。
- 不替代 Planner。

### 下一步

为需要外部知识的任务加入带来源的文档检索能力。

## v0.3.0 local-rag

### 目标

实现本地小规模文档的切分、索引、检索和来源引用，为 Agent 提供可验证的知识上下文。

### 能力

- 导入工作区内允许的文本和 Markdown 文档。
- 文档切分和稳定 chunk ID。
- 建立本地索引。
- 按查询返回数量受限的相关片段。
- 最终回答携带文件和片段来源。

### 实现思路

- 先建立检索接口和简单关键词实现。
- Embedding 和向量索引作为可替换实现，不侵入 Agent Runtime。
- 检索片段受上下文预算控制。
- RAG 结果与长期记忆明确区分。

### 可观测性

- 记录查询、命中数量、文档 ID、chunk ID 和注入字符数。
- 评估空命中、错误命中和来源引用完整率。
- 不记录完整私有文档正文。

### 边界

- 首版只处理本地文档。
- 不自动抓取任意网页。
- 不实现复杂重排序模型。
- 检索结果不直接视为绝对事实。

### 下一步

当单 Agent 的工具、计划、工作流和知识检索均稳定后，再引入任务委派。

## v0.4.0 multi-agent-lite

### 目标

引入受限的多 Agent 协作，用于验证角色隔离、任务委派和结果汇总，而不是构建开放式自治群体。

### 能力

- 定义 Coordinator 和 Worker 角色。
- Coordinator 可以创建有限数量的子任务。
- Worker 使用独立上下文执行子任务。
- 子任务返回结构化结果和来源。
- Coordinator 汇总结果并生成最终回答。
- 限制委派深度、Agent 数量和总步骤。

### 实现思路

- 多 Agent 复用同一个 Agent Runtime 类型。
- 通过不同 Options、Prompt 和工具策略区分角色。
- 子 Agent 不直接共享可变 Session。
- 委派作为一种受控 Runtime 操作，而不是无限递归调用。

### 可观测性

- 记录 parent run ID、child run ID、角色、任务摘要和终止原因。
- 汇总总模型调用数、工具调用数和失败子任务。
- 保持跨 Agent 的 request correlation。

### 边界

- 不支持 Agent 自我复制。
- 不允许无限层级委派。
- 不默认共享长期记忆。
- 不引入分布式 Agent 网络。

### 下一步

根据实际学习目标评估并行执行、成本治理、评测体系和生产级可观测性，而不是继续按功能数量扩张。

## 推荐实施顺序

近期应优先完成：

1. 清理已经完成但仍位于活动目录中的 `mini-chatbot-evolution-tool-cache` 变更，确保 OpenSpec 状态与归档一致。
2. 为 `v0.0.9 native-tool-calling` 创建独立 OpenSpec proposal、design、spec 和 tasks。
3. 先扩展 LLM 抽象和 provider 适配层，再调整 Agent 工具循环。
4. 保留文本工具协议兼容测试，确认迁移前后普通对话和工具行为一致。
5. `v0.0.9` 稳定后再进入结构化运行轨迹，暂不并行推进缓存、Memory 或 Planner。

## 版本准入原则

每个版本进入实现前必须满足：

- 在 `openspec/changes/` 中存在独立变更提案。
- 目标和非目标明确，不混入下一版本能力。
- 设计说明包含失败路径和安全边界。
- 任务拆解包含单元测试、集成测试和文档更新。
- `docs/evolution.md` 预留对应版本的能力、实现思路、可观测性、边界和下一步。

每个版本完成时必须满足：

- `go fmt ./...` 通过。
- `go test ./...` 通过。
- OpenSpec tasks 全部完成。
- 稳定能力合并到 `openspec/specs/`。
- 变更归档到 `openspec/changes/archive/`。
- `docs/evolution.md` 更新实际实现结果，而不是继续保留计划描述。
